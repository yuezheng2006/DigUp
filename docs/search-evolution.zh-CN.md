# 检索与微信历史管理演进记录

日期：2026-11-07。状态：方向已获用户确认；首批交付为决策记录和离线评测器，其余按下述验收推进。
基线：Plus `0d70d8c`，已包含 upstream `dc2651a`。关联：ISSUE-303，2026-11-07 prime-files 讨论。

## 为什么变革

产品目标是“记不清原话，也能找回自己的资料”，微信历史消息管理是核心特色：人、群、上下文和媒体必须一起工作。用户曾报告人物查询匹配无关视频、搜索数量和列表不一致、公众号误作群聊、图片缺失、导出及时间快捷项不响应。已有修复与回归测试不等于跨数据集的效果验收。分数高也不等于真实相关。

继续仅增加页面或调高一个阈值，无法说明误报是否减少、相关内容是否被漏掉，也会增加 fork 与 upstream 的冲突。需要建立“真实案例 → 可追溯证据 → 可重复评测 → 小步改进”的闭环，同时保留本地、低侵入、CLI/Skill 与 GUI 共用能力的方向。

## 参考与取舍

参考 [prime-files](https://github.com/CakeDev4k/prime-files)，本次核对 README、搜索设计、搜索引擎和缩略图源码。它面向 Windows，使用 Rust/GPUI；没有在本机运行它，也没有采用它的性能数字。

- [搜索分流](https://github.com/CakeDev4k/prime-files/blob/main/crates/nohrs-services/src/search/engine.rs)：按范围选择 backend，初始索引放后台，变更合批。借鉴职责分离与状态可见性。
- [缩略图调度](https://github.com/CakeDev4k/prime-files/blob/main/crates/nohrs-pages/src/explorer/thumbnails.rs)：快慢任务分队列、内存预算、有限重试。借鉴调度机制，不照搬 Windows Shell API 或线程数量。
- [搜索设计](https://github.com/CakeDev4k/prime-files/blob/main/docs/search.md)：SQLite 元数据 + Tantivy 全文检索不是向量混合检索。文档包含 Draft/规划内容，不能直接视为产品能力。

选择：保留 DigUp 的 embedding 和现有检索入口，先补评测、证据与范围契约，再决定是否替换文字检索组件。暂不引入 Tantivy/GPUI、重写客户端或做通用文件管理器。原因是这些变更成本高，尚无本产品数据证明收益。

其他取舍：不只提高语义阈值（可能损伤召回）；不把所有模糊查询降为精确匹配（损伤核心价值）；不增加未经校准的“置信度百分比”。纯语义结果应可辨识，明确实体查询需要可核验依据。此前人物搜索已支持文件名证据，未来须区分“文件名匹配”与“内容证据”，不能把文件名暗示成人物出现在视频中。

## 推进顺序与完成条件

### P0：检索质量可测、结果可解释

本次新增 `scripts/evaluate-search.py`，读取真实搜索输出和人工标注，产出分组指标；不生成消息，不模拟搜索，不自动标注相关性。用法见 [评测说明](search-evaluation.zh-CN.md)。

下一步在用户授权的本地固定语料上建立至少 60 条查询，覆盖中文姓名/同名、简称、模糊描述、群内时间过滤、图片/视频证据、无答案六类。每类至少 10 条；单独保留调参集和验收集。语料不足时报告缺口，不能用合成消息冒充真实验收。

在同一语料、模型、过滤条件和机器上比较改动前后；以原文、发送者、时间、命中词和媒体定位支撑结果。列表与计数必须来自同一过滤后的结果集，明确是否截断。明确姓名的无证据视频误报、跨会话泄露和计数不一致属于硬失败；测试集中为零不代表全球零风险。

验收报告包含 Precision@10、Recall@50、无答案误报率、P95、有效查询数和失败清单。先取得真实基线再设改善目标，不编造“当前召回率”。禁止用验收集反复调参后仍作为独立评估。

### P1：微信浏览与媒体预览流畅

维持左侧人/群、右侧上下文，自己的朋友圈突出显示；过滤公众号及广告属于数据类型/用户规则，不靠昵称猜群聊。头像、缓存图片优先；视频解码单独限流；只加载可见区域并取消过期任务。缓存按字节设上限，错误有限重试。

验收：快速切换会话不串图、不覆盖新结果；滚动长列表内存有界；损坏或缺失媒体不阻塞文本；本地无资源时提示缺失，不绕过授权获取。用实际媒体记录峰值内存、首屏耗时和切换延迟。

### P2：后台增量与扩展契约

消息接入、文本索引、向量、缩略图任务分离；提供暂停、取消、错误重试与进度；模型变更可失效重建，删除事件能清理旧索引，避免监听自己的缓存造成循环。授权范围必须在检索前约束，而非仅 UI 隐藏。

提炼 provider 契约：source/id、查询与范围、分页、命中依据、上下文定位、媒体能力、同步状态、取消/超时。GUI 与 Skill 使用同一服务。用兼容版本和能力探测替代硬编码路径。保留 fork 薄适配，原版宿主支持仍是待验证目标。

验收：退出窗口与退出服务行为明确；断连/重启能恢复，重跑不重复索引；范围/权限撤销后不再返回对应记录；有暂停与资源上限；CLI 与 GUI 同查询一致。

## 边界与变更留痕

- 不自动读取其他人的微信资料；真实语料、结果、身份映射保留在授权设备，不入 Git 或公开评论。附件只交付脱敏汇总。
- 不向 upstream 推送或创建 PR；同步源码与替换已安装应用分开。保留中英文回退及禁止 upstream 自动覆盖策略。
- 每次探索记录：问题与案例编号、基线 SHA/模型/语料版本、假设、选择/放弃的方案、改动、评测结果、未解决问题、回滚方式。只有通过验收才更新“已具备”列表。
- 本次新增工具不修改产品排序/媒体机制，不代表 P0 真数据验收或 P1/P2 已完成。回滚本次提交仅移除评测工具和文档，不触及用户索引。
