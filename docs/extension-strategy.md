# 扩展策略：upstream + 低侵入可插拔

产品原则（已确认）：后续能力尽量是 **upstream 本体 + 我们自己的扩展**，优先低侵入，理想形态是纯扩展、可插拔；不把业务能力永久焊进对 upstream 的大面积魔改。

## 分层

| 层 | 归属 | 例子 |
|---|---|---|
| Upstream 核心 | 上游维护 | 索引、语义搜索、设置、更新、多端壳 |
| 我们的扩展 | fork / 伴随包 | 简体中文 UI、微信／朋友圈、Skill、产品站、风险提示 |
| 宿主契约（目标） | 尽量推动 upstream 或自建薄适配 | 页面注册、数据源 provider、显式授权、版本化 IPC |

## 做与不做

- **做**：新功能先落在独立模块／CLI／Skill／伴随进程；与 DigUpKit 的边界用协议与 provider，少改上游页面与索引内核。
- **做**：每次合 upstream 时，把冲突面压在本地化字符串、薄适配层和扩展入口，而不是复制整页逻辑。
- **不做**：未获明确授权时向 upstream 提 PR，或把私有微信／密钥链路 upstream 化。
- **不做**：在 upstream 尚无扩展点时，对外宣称「原版装插件即用」。

## 现状与缺口

- Upstream 当前没有用户可安装的第三方视图／数据源插件契约；Tauri「插件」是构建依赖，不是可插拔产品扩展。
- 中文与微信能力仍在 fork 内；微信读取已抽成 reader／Moments provider／CLI，界面与读取分离——这是可插拔方向的起点，还不是完整宿主插件。
- Skill 已是进程外扩展入口，优先继续用这条路径交付 Agent 能力。

## 演进顺序

1. 固化模块边界：本地化、微信、Skill、站点各自可单独合入／关掉。  
2. 定义最小宿主接口（发现、启用、授权、侧栏注册、超时回收）。  
3. 能伴随运行的能力优先伴随／Skill；必须内嵌的再谈 fork 内页面挂载。  
4. 仅当 upstream 愿意要契约时，再讨论把接口送回上游（仍须你明确点头）。
